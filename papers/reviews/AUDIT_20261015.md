### F2. A "yes" does not name the text it is for (high)
- `process.md:308-309`: "A 'yes' already written stands unless its writer takes it back." The text voted on changed after the first post (F1). The vote template is "VOTE YES · <what> · <your name> · <date>" (`febu-assembly.html:86`); it carries no hash.
- Effect: under rule 7 four yeses adopt version 3, but a yes given on the 10-14 text is counted for the 10-15 text, which differs in rules.
- Proposed wording (Z decides; changes the vote format, so it is not applied here): the template becomes `VOTE YES · version 3 · 847a7347 · <your name> · <date>` (first 8 hex of the file the voter read), and `process.md:309` becomes "A 'yes' counts for the text whose hash it names; one written on an earlier text is asked again."

### F3. OpenTimestamps: nothing is anchored yet (high)

### F4. Non-deterministic build (medium; already fixed on main)
- `build.py` `archived()` sorted by the digits in each file name, so `v3` / `v3-answers` and `v2.1` / `v2.1-final` tied and fell back to `set` order, which changes with `PYTHONHASHSEED`. `ledger.html`, the page that prints the hash rule 6 relies on, differed between consecutive builds.
- RAN: a test that runs the build under eight hash seeds failed on `b58060c`, and a one-line tie-break made four seeds give one `ledger.html`. While this audit was under way the same bug was fixed on main (`acabe56`, "the archive table's order no longer depends on the hash seed"), also with a tie-break on the path. This branch takes main's version and drops its own duplicate. Main orders `v2.1-final` before `v2.1`; either is deterministic.

### F5. The rule allows one edit; the file made three kinds (medium)
- Rule text (`ledger.txt:99-100`): until the first SEEN line the writer "may change [WRONG IF] with a dated CHANGED line". Rule 2: nothing is rewritten; every change is a new dated line. The 10-14/10-15 CHANGED lines changed SAYS in facts 2, 4, 5, 6, 8 and WILL in PROMISE 7. The old text is kept in `archive/` and each change is dated and explained, so the spirit holds and the letter does not.
- The permission was written into the same unadopted version that it was then used to justify.
- Proposed wording: "Until the first SEEN line the writer may change SAYS, WRONG IF, WILL or BY with a dated CHANGED line that says what the old words were; after that, never. A change made before adoption is listed in CHANGES with the archive file that holds the old text."

### F6. Reopening is cheaper than closing (medium)
- Closing: two *members* other than the writer (rule 3). Reopening or splitting: two people, "member or not" (`ledger.txt:28`), and the live record's stranger lane identifies a stranger by a salted hash of the address, one post per entry per source (`live/server.py`, `api/entries.js`).
- Cost of the attack: two sources and two requests per entry. PROMISE 7 is "three entries closed under rule 3" 30 days after adoption, so two throwaway sources can hold it below three at the day-30 reading. That narrows the review's attack 1 (one account) but does not close it. KNOWN BUGS 7 says the stranger path "is not live" yet; whether `ASSEMBLY_STRANGERS=1` is set in Vercel is NOT CHECKED.
- Options for Z: (a) record it under RISKS WE ACCEPT with the cost stated; (b) a stranger-only reopening stays a NOTE until a member seconds it; (c) PROMISE 7 counts entries *that closed*, with dates, even if later reopened. (c) needs no new identity and fits the ledger's own "every change is a new dated line".

### F7. Quorum floor (low)

### F10. Secrets (info)

### F11. Two Vercel projects build the same repo (medium)
- Vercel's bot comments on this PR list two projects, `febu-assembly` and `febu-ledger`, and both built the branch's preview from the same `vercel.json`. The commit "first deploy from this repo to the febu-assembly project" (b58060c) and `process.md`'s "one project" section suggest `febu-ledger` is the older one. The post's URLs are `febu-ledger.vercel.app`.
- If both also deploy `main` to production, then: the three crons in `vercel.json` (`/api/archive`, `/api/claim?name=Zurandol`, `/api/keepalive`) run once per project; `CRON_SECRET`, `ASSEMBLY_SALT`, `ASSEMBLY_STRANGERS` and the Supabase keys are set per project, so the two can disagree (a different salt gives different stranger-lane hashes for the same source); and a failed build in one leaves the two URLs serving different files. The host rule in `vercel.json` ties the front-page route to `febu-ledger.vercel.app` only.
- NOT CHECKED (the project settings show it): which project holds the `febu-ledger.vercel.app` alias, whether the other still deploys `main`, and which has which env vars. Cheapest settle: either disconnect the repo from the project that is not meant to serve, or run `python checks/release.py --site <each project's domain> --posted <hash>` and see that both report the same file.
